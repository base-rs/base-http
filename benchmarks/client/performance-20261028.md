# HTTP client performance changes — 28 October 2026

The updated direct HTTP/1 client is faster and uses one persistent connection per request lane. The largest measured improvement is concurrent HTTPS. Hyper remains faster at the high-level client API. Connection-only measurements separate HTTP codec/transport work from client orchestration.

## Interleaved before/after results

Median completed requests/second, three repetitions of one second warmup plus three seconds measurement. The original executable (`before-open`) and updated clients run in alternating order against the same current server implementation and shared, verified self-signed certificate. Both clients use one worker, HTTP/1 without pipelining, an empty GET, and an 11-byte response. Hardware and TLS configuration match the [initial comparison](results-20261028.md).

| Transport | Concurrency | Direct Base before | Direct Base after | Improvement | Hyper pooled |
|---|---:|---:|---:|---:|---:|
| HTTP | 1 | 21,507 | 22,462 | +4.4% | 31,621 |
| HTTP | 32 | 94,402 | 103,981 | +10.1% | 125,686 |
| HTTPS | 1 | 20,318 | 20,790 | +2.3% | 30,299 |
| HTTPS | 32 | 54,227 | 90,404 | +66.7% | 114,065 |

The direct path now accepts exactly one connection per lane (1 or 32). The preserved original accepts two per lane (2 or 64), with the same pool capacity of twice the request concurrency. This improvement comes from completion handling, rather than reducing the configured pool size. All updated pooled and connection-only samples accepted exactly the configured concurrency.

## Established connections without a pool

Each lane retains its own established connection and codec state across warmup and measurement. The Base path invokes `RequestWriter`/`ResponseReader` directly; the Hyper path uses its HTTP/1 connection API and connection driver. Both still perform real socket I/O, parse every response and validate its full body. TLS progress remains supervised. Shared barriers synchronize phases and exclude connection setup/cleanup from measurement.

| Transport | Concurrency | Base connection requests/s | Hyper connection requests/s | Base CPU µs/request | Hyper CPU µs/request |
|---|---:|---:|---:|---:|---:|
| HTTP | 1 | 36,153 | 39,681 | 13.88 | 12.10 |
| HTTP | 32 | 146,033 | 140,657 | 6.81 | 7.10 |
| HTTPS | 1 | 22,903 | 31,281 | 16.90 | 15.85 |
| HTTPS | 32 | 86,798 | 125,454 | 9.41 | 7.94 |

At concurrency 32, the plain connection-only Base path is slightly faster than Hyper in this run. At concurrency 1, Hyper is faster. Adding the Base high-level client still costs considerably more than adding Hyper’s pooled client. TLS remains slower even without pooling. These observations locate further work in client dispatch/lifecycle and TLS integration; they do not identify a single function as the remaining cause. Connection-only HTTPS throughput varied substantially (Base 73.6k–92.2k at concurrency 32), so use the raw ranges when interpreting it.

## Implementation

1. **Encode validated metadata directly.** `base-http1` borrows the application fields, validates target/Host/Connection/framing rules, and encodes into a reusable per-connection buffer. It no longer clones the field collection, allocates an outbound parser header array, or reparses the generated bytes into throwaway request metadata. Request-target validation is shared with incoming parsing. Incoming traffic still uses `httparse`.

2. **Publish normal completion from the last directional owner.** Direct request/response guards return their codecs before releasing the pool use. Once both directions are successfully complete and reusable, the last owner releases the use and client admission immediately. The supervisor recovers codecs and processes the next request. Errors, cancellation and abandonment retain cleanup accounting until the supervisor retires the connection. A late cancellation cannot revoke a successfully released idle connection. Early responses alone never release an unfinished upload.

3. **Avoid redundant request-finalization waits.** A successful direct terminal write has already encoded and flushed the request; `finish` no longer waits for a second supervisor receipt. Normal synchronous `close_write` still uses supervised finalization. A fixed-length End frame emits no bytes and avoids another transport flush; length validation remains in place.

4. **Notify only TLS waiters that can progress.** Separate events cover readable plaintext, output capacity/delivery, transmit work and read-buffer capacity. Application reads notify the receiver only when leaving the full-buffer condition. Decoding notifies the transmitter when TLS has control output. Failure and shutdown still wake every affected direction. An already delivered TLS flush returns before allocating/registering a listener.

5. **Add reproducible layer measurements.** The harness now has established-connection paths and can interleave a preserved baseline executable with updated clients, retaining both source archives and executable hashes.

Public HTTP body/client semantics and scheduler interfaces are unchanged. Full duplex remains available; proxy upload and download remain concurrent. No changes were made to the scheduler checkout.

An experiment allowing application flushes to poll a retained TLS transmit future directly passed correctness tests but showed no consistent throughput improvement. Its additional boxed future, shared poll state and lifetime plumbing were removed. The final implementation retains supervised TLS I/O with targeted notifications. Exploratory stage directories are diagnostic, not additional final repetitions.
