# HTTP/1 client benchmark — 28 October 2026

Hyper/Tokio outperformed the current Base client in every keep-alive case. The direct writable API improves the single-lane TLS result relative to queued `call`, but falls behind queued `call` at concurrency 32. These measurements compare complete clients, including pooling and supervision; they do not establish that the scheduler or codec alone causes the gap.

## Keep-alive throughput

Median completed responses per second across five repetitions, each with one second of continuous warmup and five seconds of measurement. Finite pool preparation and a 50 ms settling interval precede warmup. All responses are fully consumed and validated.

| Transport | Concurrency | Base `open` | Base `call` | Hyper/Tokio | `open` / Hyper |
| --- | ---: | ---: | ---: | ---: | ---: |
| HTTP | 1 | 21,560 | 21,522 | 31,510 | 68.4% |
| HTTP | 32 | 91,501 | 90,395 | 122,131 | 74.9% |
| HTTPS | 1 | 20,267 | 16,245 | 30,364 | 66.7% |
| HTTPS | 32 | 55,113 | 66,574 | 111,867 | 49.3% |

The direct Base path completes about 25–51% fewer requests per second than Hyper in these scenarios. At concurrency 32, the queued path achieves 74.0% of Hyper’s plain throughput and 59.5% of its TLS throughput.

Queued Base and Hyper keep one connection per request lane. Direct Base uses two per lane with the configured spare capacity, despite only one in-flight request per lane. Those are connections accepted over the sample lifetime, not simultaneous outstanding requests. Connection return and driver coordination are useful profiling targets. The larger TLS gap also warrants isolating TLS progress, wakeups and buffering. These are investigation targets, not established causes.

## Reproducible setup

- Apple M4 Pro, 12 logical CPUs, macOS 27.0.1 arm64; Rust 1.87.0 optimized release build.
- One client worker: Base native/kqueue scheduler versus Tokio current-thread runtime. Hyper connection drivers and request loops are spawned tasks; Base’s scoped connection futures are polled by its single driver. This includes their current architectural differences.
- Same independent two-worker Hyper HTTP/1 server process for every sample, using loopback TCP and a static 11-byte `Hello World` response to `GET /hello`. No pipelining.
- Client TCP_NODELAY disabled for both clients, matching the current Base endpoint default. Server TCP_NODELAY enabled.
- Same rustls/ring configuration for TLS 1.3, ALPN `http/1.1`, and one local self-signed certificate with `localhost` and `127.0.0.1` subject alternative names. Both clients explicitly trust the certificate and verify the peer identity. Resumption is disabled.
- Registry Base scheduler/pool 0.2.0; local HTTP/endpoint sources; Hyper 1.12.0, hyper-util 0.1.21, Tokio 1.54.1, rustls 0.23.46. All transitive versions are locked.
- Implementation ordering rotates; scenario ordering is shuffled reproducibly. A fresh server and client process are used for each sample.

All 60 keep-alive samples passed response verification and server request accounting: **16,917,535 measured requests, zero server errors**. No compiled Rust source changed during measurement. Sources and lockfile are archived with the results; the Python runner and documentation were subsequently adjusted to add fresh-sample cooldowns.

## Interpretation limits

This is a small-response loopback saturation benchmark on a shared development machine, without CPU affinity. It does not represent larger uploads, streaming proxies, wide-area latency, HTTP/2, Linux epoll/io_uring, or multi-worker scaling. Saturation latency percentiles are retained in raw samples but are not compared here: the clients achieved different request rates, so their P99s are not equal-load latency comparisons.

The initial unprepared Hyper plaintext probe opened excessive speculative connections. It is excluded from these results. All reported keep-alive samples start with finite preparation, use persistent connections and have their connection counts retained. Direct Base’s additional connections are bounded, not continuous churn.
