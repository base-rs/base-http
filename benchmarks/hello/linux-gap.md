# Why the Linux hello benchmark trails Hyper

Investigated on Hana, 27 October 2026. The original diagnostic experiments were reverted. A subsequent compile-time OOB reader option is implemented in an isolated scheduler worktree; see the [implementation and measurements](oob-reader-option.md). Published scheduler 0.1.2 remains the ordinary benchmark default.

The measured dominant difference is one extra receive per request. The ordinary Base epoll and io_uring paths conservatively retain cached readiness after a short read, then discover exhaustion with another receive returning EAGAIN. The Hyper/Tokio path clears cached readable readiness after a nonzero short read. Instrumented counters show approximately two Base receives per response versus one Hyper receive; syscall entry/exit ranks high in the on-CPU samples.

A three-round, four-second, 64-connection diagnostic changes only native short-read clearing. Base rises from 161,737 to 183,524 requests/sec; Hyper measures 187,914. The paired median gain is 13.5%; the remaining paired difference is -2.3%. This diagnostic is not a correctness-complete patch. Whole-process Base CPU/request falls from 4.826 to 4.133 µs. Raw Native improves similarly, from 206,445 to 239,037 requests/sec; raw Tokio measures 249,013. These controls place most of the full-stack gap in readiness handling, with a smaller residual HTTP/executor cost.

Tokio 1.54.1 implements this short-read optimization in `src/io/poll_evented.rs`. `src/runtime/io/scheduled_io.rs` keeps READ_CLOSED/WRITE_CLOSED bits sticky when clearing readiness. Its ordinary TCP path uses edge-triggered Mio; it does not use the additional level/dual queues explored here.

The conservative Base behavior protects a real distinction: TCP urgent/OOB data can terminate a short normal receive while ordinary bytes remain queued after the urgent mark. The standalone Linux reproducer sends `before`, an urgent byte, then `after`, with no later peer write. Tokio reads `before` then times out, while an independent nonblocking receive obtains all five `after` bytes. This reproduces both with and without a socket alias consuming the urgent byte before event delivery. Blindly copying short-read clearing would import that limitation.

Several diagnostics explored ways to preserve the stronger behavior. Deferred retry recovered only part of the gap and raised low-concurrency CPU cost. Always-on level read notification approached the short-read diagnostic, but can spin on unread input when consumers apply backpressure. A secondary level queue added complexity and worse latency, without establishing an advantage. One-shot io_uring read polls improved its screen but introduced per-read registration work. These experiments are preserved as evidence and were reverted; none justifies a new default backend architecture. The authority-scanning screen did not establish a repeatable gain and was not retained.

A follow-up Linux loopback test exercises a real Hyper 1.12.0 HTTP/1 server with pinned Tokio 1.54.1. An ordinary complete request responds in about 69 µs. With an urgent byte between two portions of an otherwise complete request, the response stalls for the entire 400 ms observation window when the header deadline is disabled. Explicitly configuring a 100 ms header deadline and Tokio timer closes the connection with `HeaderTimeout` (about 81 ms after the 20 ms setup delay). No socket alias or additional peer traffic is involved. This demonstrates a peer-triggered per-connection stall, but does not demonstrate a deadline bypass, CPU spin, memory corruption, or a global runtime stall. Connection resource exhaustion is a potential availability impact; ordinary incomplete requests already retain resources without deadlines. No advisory classification or broad deployment exposure has been established.

The follow-up [OOB reader option](oob-reader-option.md) now implements that policy for native epoll, with OOB support disabled by default and a conservative compile-time opt-in. EOF remains sticky; observed urgent data is rejected by the fast scalar path. io_uring retains its conservative implementation because its multishot poll can report advisory priority bits for ordinary TCP wakeups. The level/dual-queue experiments remain unnecessary to match Tokio's ordinary epoll short-read behavior.
