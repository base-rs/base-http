# Direct reader/writer waker experiment

The user explicitly requested the most direct single-reader/single-writer comparison to measure the possible advantage of dedicated slots. This is a temporary experiment, not a production capability change. Production readiness_driver.rs was restored in finally before timing, and its rebuilt release binary matches the preceding native-events baseline byte for byte. The experimental binary, exact source, diff, build script and hashes remain frozen here.

Each Direction embeds Mutex<Option<Waker>>. Waiting clones the current waker, replaces that slot under its lock, drops the old waker outside the lock, then rechecks closure/readiness. Publication takes the slot under lock and wakes it outside. There is no Notification, listener object, listener ID, collection scan, cutoff tracking, abandonment guard or concurrent-waiter fallback. Generation handling, byte hints, EOF, dispatch, socket I/O, protocol framing and connection supervision remain unchanged. This deliberately changes waiter storage size and future layout along with removing bookkeeping; it does not measure one isolated instruction or atomic.

Both independent reviewers found no lost-wakeup defect with exactly one live waiter per direction. Read and write have separate slots. Store-before-recheck covers events/closure before installation, while later publication consumes and wakes the slot. All clone/drop/wake callbacks remain outside the slot lock.

This prototype cannot satisfy the full scheduler concurrency and abandonment requirements. A second same-direction waiter replaces the first. A finished, cancelled or abandoned wait can retain a stale task waker until replacement, notification, group close or registration destruction; this may retain task/captured resources. Thus no production cancellation, alias-concurrency, forgetting or general duplex-conformance claim is made. Applicable scheduler context/design.md and context/io.md and HTTP design/implementation.md and design/duplex.md remain unchanged in production. The raw and static HTTP benchmarks fit the narrower one-reader/one-writer topology.

Five focused stream-reader tests, seven readiness-writer tests (including real TCP backpressure), collected-pointer retirement and cross-worker closure fixtures pass against the experimental test binary. An initial writer filter accidentally selected one unrelated test; its log remains writer-initial-filter.log. After throughput timing, the correct readiness_tests filter ran against the preserved candidate executable and passed all seven cases; provenance records its hash and command. No test, build, profile or other load ran concurrently with throughput timing. Raw response/reuse/half-close validation and 10,000-request sequential raw/static HTTP diagnostics pass; each sequential request has one positive read and write.

The comparison environment's source hashes describe the restored working tree; direct-readiness_driver.rs and provenance.json identify the compiled experimental source. These are deliberately distinct. Runtime checks cover the scoped candidate, not all scheduler contracts; the previous complete coverage result continues to describe the unchanged general implementation.

The first cohort has 30 zero-error samples (five interleaved eight-second samples per variant); the raw confirmation adds 15 (five interleaved five-second samples per variant). User CPU does not improve consistently: raw is 3.6% higher initially and 3.1% lower in confirmation, with mixed paired signs in both; HTTP differs by 0.3%. Raw throughput changes +1.2% and then −1.7%. No repeatable performance advantage or Tokio/Hyper throughput win is established. The general implementation remains retained. See results.json and confirmation/results.json for paired calculations; placement/activity/kernel variation is uncontrolled.
