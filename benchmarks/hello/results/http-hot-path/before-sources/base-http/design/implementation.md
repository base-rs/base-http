# Implementation and scheduler coordination

Updated 2026-10-26. The initial semantic core, pull bodies, native HTTP/1 client/server codec and application server are implemented. The sibling `base-pool` now implements generic singleplex and multiplex pools. All HTTP packages and the pool remain unpublished prototypes. High-level client orchestration, HTTP pool integration, TLS, compression, QUIC and HTTP/2/3 remain planned.

## Package boundaries

- `base-http` owns generic requests/responses, scalar types, ordered `Fields`, body traits and in-memory bodies.
- `base-http1` owns HTTP/1 parsing, framing, read-ahead, interim transmission, persistence and managed protocol switches.
- `base-http-server` owns generic application handlers, accepted sockets, bounded listener admission, cancellation, joining and closure.
- [base-pool](../../base-pool/readme.md) owns distinct exclusive leases and shared-use reservations, bounded construction, FIFO acquisition and explicit retirement. It has no HTTP dependency; HTTP connection integration remains planned.

The packages are independent siblings with explicit local path dependencies for unpublished HTTP crates. Scheduler dependencies declare the published `0.1.0` interface and are patched to the sibling `base-scheduler` workspace for development and validation. No parent Cargo workspace is introduced over unrelated projects. `base-http1` privately uses `httparse` for request/response heads. The server uses `FuturesUnordered` for supervised connection futures; it does not spawn or detach tasks. No `http`, `http-body`, Hyper or Tokio runtime is a production dependency.

## Semantic core

`Request<B>` and `Response<B>` carry public heads and arbitrary body owners. Dereferencing exposes head members. `map_body`, `with_body`, `into_parts` and `from_parts` preserve ownership without cloning or erasing the body type. `Method`, `Status`, `Version` and `Protocol` retain the previously reviewed semantics. `101` is informational but final, and every successful 2xx CONNECT establishes a tunnel.

`Fields` stores ordered `pairs`, one optional trailer boundary, a lazy semantic index and policy overrides. Names retain spelling; values are validated bytes. Raw inspection uses immutable access; interpreted lookup takes mutable access. The index combines comma/cookie values, preserves separate cookies/challenges, rejects duplicate singletons and applies trailer policy. Field-specific date/range/authentication/negotiation parsers remain follow-up work.

Short names and values (up to 24 bytes each) and the first pair have inline storage, with heap fallback for longer data and larger collections. The index and custom policy tables are separately allocated only when used, keeping ordinary raw messages smaller. Construction accepts `AsRef<str>` names so borrowed names need no temporary `String`. This prototype bound replaces `Into<String>`; custom name types must implement `AsRef<str>`. Public accessors still return `&str`, byte slices and an ordered field slice, and cloned fields remain independently mutable.

## Body interfaces

`ReadableBody` now combines asynchronous cancellation-aware chunk reads with readiness, exhaustion, total representation length, replay, closure and trailer completion. `WritableBody` describes whole-chunk producer writes, flushing, write closure and abandonment. Concrete `BodyReader<D>` and `BodyWriter<D>` implement those traits. `BodyWriter` also has inherent producer methods. `BodyReader::bounded(max_bytes, max_chunks)` returns the pair; `with_length` additionally declares representation length.

`EmptyBody`, `BufferedBody<D>` and `HeadBody` retain their earlier behavior. `BufferedBody` stores zero or one chunk inline and uses a vector for multiple chunks; its slice view, independent replay cursor and append-after-close behavior are unchanged. Total representation length survives reads and close; a HEAD body may emit no data while retaining a nonzero length. Empty chunks are data. Queue limits include empty chunks; oversized chunks fail immediately. Normal writer closure preserves queued chunks through EOF. Failure discards queued chunks and preserves its cause. Dropped endpoints wake blocked peers. Pre-cancellation and dropped pending writes do not mutate the queue. Notifications and arbitrary chunk destruction occur outside the mutex.

There is one pull abstraction. The earlier `BodyStream`, `StreamableBody`, `StreamBody`, `ReadBody` and `WriteBody` interfaces are removed. A driver runs body reads within its existing future. A custom body can consume incoming input while yielding outgoing data. Imperative producers use explicitly supervised concurrent work with the bounded queue. Application chunks need not implement unsafe completion-I/O buffer contracts.

`Request::read` and `Response::read` invoke `ReadableBody::finish(&mut Fields)` at EOF. An incoming body has already parsed its trailers and moves them into the message after its existing split marker. The hook is synchronous and idempotent; it performs no retirement. Direct `body.read` callers invoke it explicitly. Output drivers invoke it before serializing trailers. A known-length producer generating trailers declares the boundary or `Trailer` field before transmission; fixed framing cannot change at EOF.

## HTTP/1 behavior

`RequestReader<R>` owns the input lane and read-ahead. It validates configured limits, strict CRLF, targets and Host, rejects ambiguous Content-Length/Transfer-Encoding, and supports fixed/chunked request bodies. Duplicate Content-Length is rejected even when values match. Only the chunked transfer coding is implemented. Chunk extensions are syntax-checked and ignored. Trailer fields use the semantic split and eligibility checks. Failed or abandoned started reads poison reuse; pre-cancellation preserves input.

`IncomingBody<'a, R>` borrows the input lane. `Exchange` shares immutable framing facts and completion/switch state through one `Arc`: HTTP version, HEAD/CONNECT classification, persistence, Expect/Continue and upgrade offers. Only upgrade offers retain copied field bytes. The application's path, authority and ordinary fields have a single owner in its independently mutable request head. Mutating that head cannot change established framing or authorize an unoffered upgrade. The former `Exchange::head()` accessor is replaced by framing accessors such as `version()`, `is_head()` and `is_connect()`. `ResponseWriter<W>` owns the independent output lane, retries short writes, rejects zero progress, checks fixed lengths, and emits fixed, chunked or HTTP/1.0 close-delimited data. HEAD, 204, 304 and 205 rules receive explicit handling. Known trailers select chunked framing; generated framing fields stay in the wire head even when the message already has a trailer boundary. Trailer eligibility is checked independently of application policy overrides. Ordered repeated fields are preserved.

`InterimResponses<InterimWriter<W>>` transmits and flushes explicit 100/102/103 heads before the final response. A failed/abandoned started wire write poisons output. HTTP/1.0 interim responses are rejected. When an upgrade request also expects 100-continue, the writer ensures 100 precedes 101. Raw Upgrade fields can also advertise support in ordinary responses. Incoming requests are handled sequentially; coalesced/pipelined requests remain buffered for subsequent admission.

`Exchange` distinguishes completed, active and abandoned input. A final response can begin while its request body remains active; the output persistence result is eligibility, not proof of connection synchronization. Admission waits for completed input/output and joined concurrent work. Dropping or closing unfinished input disables reuse; no unread upload is silently drained. Streaming echo can therefore reuse its connection after consumption finishes. A parse error receives best-effort 400 or 431 followed by closure. Application/late body errors close the connection; automatic application-error-to-500 handling is not implemented.

For 101 and successful CONNECT, the response handshake is flushed and incoming reads become raw bytes. Read-ahead is preserved, framing fields are prohibited, and future HTTP admission stops. A handler can return the incoming body for a statically dispatched duplex echo. The server retains cancellation, accounting, lane retirement and socket closure throughout. No raw socket is handed to the application. Independent producer/input task orchestration beyond the returned body remains an application responsibility; the server does not create a detached input task when response production finishes.

`RequestWriter<W>` and `ResponseReader<R>` expose native client lanes and reuse the common body encoder/decoder. The writer validates targets/Host before output, flushes the request head before pulling its body, frames fixed/chunked uploads and trailers, and closes the body on return. HTTP/1.0 requests cannot be close-delimited. The reader delivers interim heads, handles HEAD/bodyless responses, validates framing and reads fixed/chunked/close-delimited data. All 2xx CONNECT responses ignore framing fields as required by RFC 9112; 101 validates the selected offered token. These switch responses expose raw incoming bytes and permanently disable HTTP reuse. Coordinating managed bidirectional client switch output remains unimplemented.

No request queue, endpoint establishment, pool or Expect/Continue wait policy is hidden in these primitives. A caller supplies the matching request head, supervises both directions and owns socket retirement. The [duplex experiment](duplex.md) verifies this using a three-party proxy. The next high-level client driver must retain upload work across `call` return while preserving the ordinary handler response contract; this orchestration is not yet implemented.

## Application and scheduler lifecycle

`Handler` is generic over incoming body and interim hook types. Its associated `Body<B>` selects the outgoing body type without boxing; echo uses `B`, static handlers use `BufferedBody`, and imperative producers use `BodyReader`. The associated response type depends on the incoming body, while the interim hook is borrowed only during `call`. This prevents a returned body from retaining the response writer needed to serialize it.

`serve_connection` consumes an accepted scheduler socket. It constructs independent bound reader/writer handles once, serves exchanges, awaits both uncancellable lane closures even after error or cancellation, drops the handles, then exclusively closes the socket. Cancelling interrupts handler and output-body futures even if they ignore the passed signal. Dropping the whole serving future is not a cleanup join; callers cancel cooperatively and await it.

`serve` consumes an already-bound listener, caps concurrently owned connection futures, retains a pending accept across other connection completions, stops acceptance on cancellation, cancels active exchanges, joins their retirement and closes the listener. It reports aggregate connection/request/error counts and isolates peer failures. This shutdown terminates in-flight work; timed graceful draining and deadlines remain future policy. The server requires no scheduler `Spawn`, `Clone` or static application handler.

The input path reads directly into initialized per-connection parser storage, retaining spare storage across reads and publishing only successful read counts. Head parsing borrows that storage; returned body chunks still own copies. Request/response head parsing uses safe uninitialized stack storage for up to 100 fields, with heap fallback for larger configured limits. The exact configured field limit still applies. Common method tokens use borrowed constants; extension methods retain their original spelling. Response framing borrows the semantic head and describes generated wire fields separately, avoiding a cloned field collection, temporary decimal strings and trailer-name joins. Generated fields do not mutate the application's head.

Output batches headers, framing bytes and immediately available small chunks into a reusable buffer capped at 16 KiB. Large slices bypass the copy buffer. Status lines, fields and trailers serialize incrementally, so a large head or trailer section does not enlarge the retained output buffer. Ordinary static response headers and body share a transport write. The body readiness predicate remains a hint: before awaiting an actually suspended read, the driver flushes pending output and then awaits the same started read future. This includes incoming bodies with partial chunk framing. Interim responses, tunnel handshakes and client request heads flush explicitly before further input/production. A failed or abandoned write leaves output poisoned; closure discards pending bytes without retrying them.

These changes preserve generic bodies and the independent input/output futures. Output still uses the scheduler's borrowed scalar writes. Owned submissions, frozen receive leases and vectored output remain measured optimization opportunities. Backend closure follows the released [I/O guide](../../base-scheduler/context/io.md).

The [cost-reduction report](../benchmarks/hello/hyper-target.md) records the compact exchange, borrowed wire plan, inline fields and native readiness changes with preserved source/binary evidence and Hyper controls.

Handler and body waits skip cancellation-listener work for `Cancellation::never()`. Cancellable handlers and bodies still have their futures raced against the signal, including implementations that ignore the supplied signal themselves.

## Validation and remaining scope

Semantic tests cover field policies, body mapping, readiness/length/replay, queue backpressure/cancellation/abandonment and interim sequencing. The bound-file-reader test retains separate asynchronous resource retirement.

HTTP/1 deterministic tests vary fragmentation, force one-byte output writes, check zero writes, short/long bodies, output poisoning, target forms and static trailers. Real TCP tests use the local Direct scheduler and an independent raw peer. They cover fixed/chunked streaming, persistent/pipelined requests, trailer delivery, interim-before-upload, bodyless responses, close-delimited HTTP/1.0, bounded producers, malformed framing, truncation, cancellation, listener limits and managed duplex upgrades/CONNECT with coalesced input and half closure. A runnable server example additionally supports independent tooling such as curl. Batching regressions cover one-write static responses, an inaccurate readiness hint without restarting the read, bounded batches before body completion, large fields/chunks/trailers, write failure without replay on close, parser limits on both sides of the stack threshold, and streaming echo stalled on a partial chunk delimiter. Client codec tests cover fragmentation, interim ordering, response trailers, bodyless responses, close-delimited input, invalid framing, truncation, abandonment, cancellation and switch classification. Three-party proxy tests demonstrate streaming, interim/trailer forwarding, response completion before upload production, 8 MiB transfers with delayed response consumption, reuse of both connections, and cancellation/error cleanup of all four lanes.

The API remains a prototype. Native client framing exists, while high-level client/pool orchestration and managed client tunnel coordination are not implemented. The proxy experiment explicitly owns and joins upload/download futures; it is not a drop-in high-level proxy handler. Broader fuzzing/interoperability, upgrade protocol/version representation, deadlines, TLS and alternative runtime backends remain follow-up work. The current semantic `Protocol` stores one token; raw upgrade offers are retained, while selection is limited to one token. This is not a complete upgrade negotiation framework or full RFC conformance claim. Linux io_uring behavior and performance have not been measured on this macOS host.

The [static hello comparison](../benchmarks/hello/results.md) adds a release-build performance baseline on macOS for native readiness, Tokio and Direct backends against Hyper/Tokio. This covers one application worker, persistent connections and a 13-byte response. The [integrated optimization comparison](../benchmarks/hello/http-optimization.md) records the production batching/allocation changes against a saved unchanged-HTTP binary using the same local scheduler. The [harness](../benchmarks/hello/readme.md) records settings and raw samples; it does not establish full alternative-backend conformance or Linux io_uring throughput.
