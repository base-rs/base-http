# Build roadmap

Updated 2026-11-21. This is the ordered implementation plan for the [semantic design](proposal.md), informed by the [source review](source-review.md) and [component evaluation](components.md). It describes planned work; the [implementation notes](implementation.md) record completed code and checks. The [client/connection taxonomy](client-connection.md) defines negotiation on both client and server paths and a unified HTTP client pool contract. The [HTTP/2](http2.md), [protocol switching](protocol-switching.md), [QUIC and HTTP/3](http3.md), [stateless QUIC routing](quic-routing.md), [load balancer](load-balancer.md) and [middleware](middleware.md) requirements, detail M6 to M11.

The first application milestone is a streaming HTTP/1 client and server over plain TCP, with connection reuse and explicit shutdown. HTTPS follows, then the version-neutral connection contract and the opt-in spawned connection mode that HTTP/2 needs, then HTTP/2. Native QUIC is a separate transport milestone before HTTP/3; stateless routing of QUIC datagrams follows, relying on the connection-identifier format QUIC adopts from the start. Each protocol should become independently usable and interoperable as it is added.

## Starting point and boundaries

The semantic core and pull-body model are implemented, together with the first native HTTP/1 server path in sibling `base-http1` and `base-http-server` packages. Tests exercise streaming, persistence, interim responses, trailer delivery, managed upgrades/CONNECT and cancellation over real TCP on the Native scheduler. A deterministic transport covers fragmentation and partial writes. Native HTTP/1 client framing and a duplex proxy experiment now exercise both directions. Generic singleplex and multiplex pools are implemented independently in sibling [base-pool](../../base-pool/readme.md). The scoped high-level HTTP/1 client now integrates capacity-one multiplex admission and independent upload/download; transient borrowed-body proxy integration, managed client tunnels and other backends remain follow-up work. HTTP/1 HTTPS and shared protocol factories are now implemented; see [transport layering](transport.md). See [implementation evidence](implementation.md).

The scheduler rename and release are complete: `base-scheduler` and its companion crates are published, six of them in the `0.5.0` family. The HTTP packages use that family and Rust 1.87, including the corrected socket-handle lifetime contract and `try_read_into`, on which the client's idle-connection check relies. The 0.5 family removed the Direct backend and added Native stall rescue. See the [published interface](https://crates.io/crates/base-scheduler/0.5.0) and [scheduler release](https://github.com/base-rs/base-scheduler/releases/tag/v0.5.0).

`base-pool 0.2.0` was published via `aiko.local` on 2026-10-28 and verified through the registry-backed client on macOS and Linux. It adopts scheduler 0.2 and Rust 1.87; its API remains experimental. The scoped HTTP/1 client now exercises its admission and retirement contracts; pool performance measurements and shorter-lived borrowed-body forwarding remain required. The HTTP packages now use `base-pool 0.5.0` and `base-endpoint 0.3.0`, as recorded in the [release notes](../releases.md); CI runs the workspace tests with them on Linux, with the current stable Rust and with Rust 1.87, and the client benchmark runs on Linux. See the [pool release notes](https://github.com/base-rs/base-pool/blob/main/releases.md).

The planned package boundaries are:

- `base-http` owns semantic messages, `Fields` and bodies in `base_http::body`. The [middleware](middleware.md#shared-request-interface) requirements add the request interface that server handlers and the client both implement, `Handler<C>`, with the downstream `Peer` in its server context.
- `base-http1`, `base-http2` and `base-http3` own protocol-specific connection APIs and drivers.
- `base-http-client` and `base-http-server` compose the enabled protocols into application APIs. The client also uses `base-pool`.
- `base-pool` implements distinct `SingleplexPool` and `MultiplexPool` contracts with a common admission interface. The HTTP client uses `MultiplexPool` with capacity one for HTTP/1 and negotiated stream capacity for HTTP/2/3. The HTTP/1 client exercises this integration; additional protocol consumers and measurements remain required before API stabilization.
- `base-http-hpack` and `base-http-qpack` own compression interfaces. Each is a native implementation behind its Base-owned interface, decided on 2026-11-20: `base-http-hpack` ports `protocol-hpack`, and an independent codec is only a development dependency, as a test oracle. Upstream types do not become public aliases or re-exports in the codec API. No pluggable backend framework is required.
- `base-http-protocol` owns shared HTTP engine selection and client/server connection factories. The current factories return HTTP/1 codec pairs; M6 replaces them with selected connections, as [HTTP/2](http2.md#connection-contract-and-protocol-selection) requires.
- TLS currently lives in `base-endpoint::tls`, including optional rustls and supervised duplex I/O. Extraction into `base-tls` remains optional. Native `base-quic` uses rustls's separate QUIC handshake/key API; `base-http3` uses QUIC connections.
- `base-quic-wire` and `base-quic-router` are sub-crates of the `base-quic` workspace (`crates/wire`, `crates/router`). `base-quic-wire` owns QUIC's version-independent header parsing and the connection-identifier format shared by `base-quic` and `base-quic-router`, without TLS, scheduler or HTTP dependencies. `base-quic-router` forwards QUIC datagrams to endpoints by connection identifier without terminating TLS; see [stateless QUIC routing](quic-routing.md).
- `base-http-proxy`, a sub-crate of this workspace at `crates/proxy`, provides the proxy forwarding handler over the client and server. The load balancer application lives in its own repository, `base-load-balancer` as a working name, composing it with the router; see the [load balancer](load-balancer.md).

Create packages when their implementation starts, using sibling HTTP packages with explicit local path dependencies while they are unpublished; avoid creating a parent workspace over unrelated projects. A separate repository or published release is not a prerequisite for the next local consumer. Hyper and the `h2` engine remain external comparison peers; focused parser dependencies are allowed, while the HPACK and QPACK codecs are native and use independent codecs only as test oracles.

## Ordered milestones

| Stage | Deliverable | Usable result |
| --- | --- | --- |
| M0 — complete | Scheduler rename and release | Interface and all seven companions are published at `0.1.0`. |
| M1 — core implemented | Semantic messages and fields | Applications construct and transform native requests/responses. |
| M2 | Streaming bodies and owned-buffer transport lifecycle | Bounded producers/consumers, pull bodies and bounded producer/consumer endpoints and supervised I/O with demonstrated cleanup. |
| M3 | Native HTTP/1 connection APIs | One streaming exchange, then persistent exchanges, over memory and TCP. |
| M4 | Client/server orchestration and capacity-one multiplex admission | First application milestone: a reusable plain HTTP/1 client and server. |
| M5 — initial path implemented | TLS and client/server negotiation | HTTPS client/server using the same HTTP/1 engine and explicit protocol selection. |
| M6 | Version-neutral connection contract and an opt-in spawned connection mode | The HTTP/1 client and server select and dispatch connections rather than codec pairs; besides the scoped mode, an application can choose a mode in which each connection is its own task. |
| M7 | HPACK, HTTP/2 and dynamic multiplex admission | Concurrent HTTP/2 exchanges through the same application and pool contracts. |
| M8 | Native QUIC transport | Independently interoperable QUIC streams, without HTTP, issuing router-compatible connection identifiers. |
| M9 | QPACK and HTTP/3 | HTTP/3 through the shared semantic and application APIs. |
| M10 | Stateless QUIC routing | Several QUIC endpoints behind one address, routed by connection identifier without TLS termination, with replies through the router or by direct server return. |
| M11 | Load balancer | Stateful proxying of HTTP/1, HTTP/2 and HTTP/3 to upstream groups, and stateless QUIC routing, separately or in one process. |

This is dependency ordering, not a calendar estimate. HTTP/2 and QUIC are substantial implementations. `base-quic-wire` and the router's decision logic depend on no transport state and can be built alongside M7 or M8; M10's integration evidence needs M8 endpoints. Focused experiments can happen earlier where they resolve a current interface question; the full later engines need not be prerequisites for the HTTP/1 path.

### M0: scheduler rename and release — complete

The original scheduler milestone published the `0.1.0` family. The pooled-client work adopted `base-scheduler 0.2`, `0.3` raised the minimum to Rust 1.87 for precise socket-handle lifetime captures, `0.4` added `try_read_into`, and the HTTP packages now use the `0.5.0` family. Use one consistent scheduler version across the graph; a deliberate local override is available if later co-development requires it.

The release uses explicitly constructed, scheduler-bound reader/writer handles, with cancellation per operation and uncancellable handle closure for retirement. Protocol objects may retain these capabilities; a handle does not switch schedulers between calls. The old prototype's per-read scheduler switching is historical evidence, not a requirement of the released API.

**Completed evidence:** all eight `0.1.0` packages are present on crates.io and not yanked. The HTTP prototype now uses the released dependencies with registry checksums in its lockfile.

### M1: shared semantic core — implemented

The package/import rename and scheduler migration are implemented. `ReadableBody::read` now takes cancellation only, and the file-body integration test borrows a released bound reader with separate asynchronous cleanup. Existing body behavior remains intact.

`Fields` implements raw ordered `pairs`. Explicit `HttpHeaders` interpretation owns the lazy policy index, combination/trailer defaults, custom overrides and provenance of appended trailers. Moving interpretation onto `base-message` interprets trailers as a section of their own, as [trailer interpretation](trailer-interpretation.md) requires. Indexing and indexed mutations validate singleton rules; failed mutations preserve previous state. Rich date/range/authentication/negotiation parsers remain focused follow-up work, distinct from combination.

Method/status/version, protocol intent and request-target components are implemented with `Request<B>`/`Response<B>`, public `RequestMetadata`/`ResponseMetadata` and `.metadata`, consuming `map_body`/`with_body`, and `into_parts`/`from_parts`. Informational and final responses share the response representation; exchange sequencing belongs to the protocol/responder API.

Existing static bodies remain usable. Generic body transformations are tested without cloning, body trait bounds or boxing. Prototype optional `BoxBody` when a real heterogeneous return boundary needs it, explicitly choosing its chunk/error and future erasure.

**Completed core evidence:** behavior tests cover field order, duplicates and policy errors, explicit trailer accumulation, header/trailer iteration, request-target forms, status predicates, body mapping and preservation of metadata/body ownership. Readiness, EOF, representation-length and replay behavior remains intact. Tests, README examples, Clippy and Rust 1.85.1 checks pass; see [implementation scope](implementation.md).

### M2: prove streaming and I/O ownership — initial path implemented

`ReadableBody` combines observations and lazy reads; `WritableBody` describes producer operations. `BodyReader`/`BodyWriter` bound bytes and chunks. There is no separate callable-stream abstraction. A handler can return incoming input as its outgoing body without spawning. `InterimResponses` provides explicit interim sequencing.

Body reads now deliver owned `BodyFrame` data/headers with an `end` flag or a separate `End`. Message reads leave initial fields untouched; callers explicitly append trailers or forward whole frames through `write_frame`. The old `ReadableBody::finish` hook is removed. Real TCP tests exercise streaming, backpressure, cancellation and managed duplex use. The server awaits both lane closures and drops the handles before closing sockets. Cancellation also interrupts handlers and output bodies that ignore their signal.

**Remaining evidence:** TLS storage/progress experiments, pooled receive-buffer optimization, and broader runtime verification on Tokio and Linux io_uring. The initial driver uses bounded borrowed parser reads and copies returned chunks. A [static hello benchmark](../benchmarks/hello/results.md) exercises the native readiness and Tokio backends; its recorded macOS results also include the Direct backend, which scheduler 0.5 removed. It does not establish the remaining streaming/cancellation or Linux performance evidence.

### M3: native HTTP/1 — initial client/server codecs implemented

`base-http1` provides `RequestReader`, `IncomingBody`, per-request `Exchange`, `ResponseWriter`, client `RequestWriter`/`ResponseReader`, interim hooks, configurable parsing limits, fixed/chunked framing, close-delimited responses, trailers and persistence. Server upgrades/CONNECT retain managed duplex bodies; client switch parsing exposes raw input, while outgoing client switch coordination remains planned. Native code parses heads and trailers and owns framing and connection decisions.

The tests include fragmented and coalesced messages, ambiguous framing, truncation, partial/zero writes, interim/final sequencing, static and computed trailers, bodyless responses, cancellation and upgrade read-ahead. The raw TCP peer is independent of the Base codec. Early final responses permit reuse when active uploads finish; abandoned uploads disable reuse. No unread upload is silently drained. The [proxy experiment](duplex.md) checks complete early responses, independent upload/download progress, interim/trailer forwarding, two-connection reuse and joined failure/cancellation cleanup.

**Remaining:** managed client tunnel coordination, high-level exchange supervision, broader protocol interoperability/fuzzing, deadlines, protocol-version upgrade identifiers, supported alternative scheduler backends and Linux measurements. This is an initial implementation, not a completed production-conformance milestone.

### M4: build the application client/server and HTTP connection pool

The initial `base-http-server` now exists with bounded connection futures, generic handlers and cooperative shutdown with joined retirement. Generic `base-pool::SingleplexPool` and `MultiplexPool` are also implemented, with bounded construction, FIFO/cancelled waiters and explicit retirement; a TCP test checks resource reuse and retirement accounting. The scoped `base-http-client` now implements client-owned upload supervision behind `call`, following the [symmetric application contract](duplex.md#symmetric-application-interface), and integrates `base-pool::MultiplexPool` with `Admission::concurrent(1)`. The prototype returns on final response headers and keeps upload progress independent of response reads. Composing a longer-lived client with an ordinary proxy handler's transient borrowed incoming body remains follow-up ownership work. Application request/response producers use the same bounded body pair; handlers continue to return responses. Keep HTTP construction policy in the client. Exercise construction permits, use reservations, abandonment cleanup, cancelled waiters and supervised retirement through actual HTTP connections.

The client owns endpoint establishment, driver supervision and reuse. Establish the [protocol-selection boundary](client-connection.md) on both client and server even while configured HTTP/1 is the only engine. Reserve capacity before establishment, register the selected connection's progress owner and then publish admission. The active use remains charged until both directions are finished and the connection is synchronized or retired. Begin with conservative retry behavior; automatic retries require known processing state, semantic retryability and a reproducible body.

The server supplies bounded connection/handler admission, request handling and graceful shutdown. Test cancellation and error responses while a request upload is still active. Stopping the server must stop admission, drain or terminate admitted work, await owned drivers and close transports after retirement.

**Exit evidence:** an executable streaming client/server example, repeated requests over reused connections, saturation/cancelled waiters, stale connections, construction-limit races and shutdown with in-flight bodies. This is the first usable application milestone. Preserve the direct `base-http1` APIs for callers that do not need orchestration.

### M5: add rustls TLS and HTTPS

The initial path uses optional rustls in `base-endpoint::tls` for configuration, verification, handshake/progress, retained TLS state and shutdown. Supervised duplex I/O supports HTTP/1 client/server traffic. `base-http-protocol` supplies ALPN and selects the HTTP factory above the transport; `base-http1` sees plaintext only. Missing-ALPN compatibility is configurable and unknown selections are rejected. No separate `base-stream` or `base-tls` crate is required by this first integration. Deadlines, broader fault injection and measurements remain follow-up work.

**Exit evidence:** independent HTTPS peers, certificate/hostname failures, fragmented records, partial ciphertext writes, retained plaintext, required TLS traffic during application backpressure, cancellation, truncation and closure. Measure copies, record batching and retained bytes. Exercise HTTP/2 ALPN selection when M7 is available.

### M6: version-neutral connections and schedulable drivers

Replace the `base-http-protocol` factories' HTTP/1 codec pairs with selected connections, a closed enum over the engines compiled in, and extend `HttpProtocols` with the enabled engines in preference order and a plaintext policy, as [HTTP/2](http2.md#connection-contract-and-protocol-selection) requires. Make the server and client error and option types version-neutral. Initially HTTP/1 is the only variant; the change lands before HTTP/2 so that its effect on the HTTP/1 path can be measured alone.

Resolve the [task placement](client-connection.md#writable-http1-experiment-and-task-placement) question as decided on 2026-11-20. The scoped mode stays: connection drivers are supervised within the client's or server's own operation, with borrowed handlers, bodies that need only outlive the scope and no scheduler `Spawn`. An opt-in spawned mode, chosen per client or server, makes each connection its own task. It requires the scheduler's `Spawn` and `Send + 'static` handlers and bodies. In both modes, client-wide and server-wide supervision keep owning admission, cancellation and joined retirement, and the direct HTTP/1 client path keeps running in its calling tasks.

Move the server's `Handler` into `base-http` as the [shared request interface](middleware.md#shared-request-interface), `Handler<C>` with `ServerContext` carrying the downstream [`Peer`](load-balancer.md#connection-information-and-the-proxy-protocol), in this milestone, decided on 2026-11-20, since both it and the version-neutral errors change the handler interface, so applications adapt once. HTTP/3's early-data flag (M9) and the load balancer (M11) depend on it. The client implements the interface as [middleware](middleware.md#shared-request-interface) records, decided on 2026-11-21: server request bodies become owned, the interface carries the scope lifetime they outlive, `ReadableBody`'s data implements `Chunk`, converting into `Vec<u8>`, and the server's entry points declare `Send` futures. The client's `call` is replaced, as decided on 2026-11-21, by one on the direct path that moves an upload unfinished at the response head to the driver and returns a streaming response body, which the spike measured at the direct writer's per-request cost; it relays interim responses, and `open_request` stays; until the client implements the interface, it keeps its existing `call`.

**Exit evidence:** server handlers implement `Handler<C>` and observe the `Peer`; the client implements it with owned request bodies, a handler forwards a request body through it without copying, and the per-request cost of the client's `call` against the direct writer is recorded; the existing HTTP/1 suites and examples pass unchanged in behavior in the scoped mode, and the same scenarios pass in the spawned mode; HTTP/1-only builds pull in no new dependencies; in the spawned mode, connections of one client and one server progress on more than one worker; the hello and client benchmarks are rerun in both modes against the M5 baseline on matched hardware, and any regression is recorded and justified.

### M7: add HPACK, HTTP/2 and multiplex admission

The [HTTP/2 requirements](http2.md) detail this milestone, including the reviewed defects of `protocol-http2` that must not carry over. First implement `base-http-hpack` as a native port of `protocol-hpack` behind its Base-owned interface, as decided on 2026-11-20: independent encoder/decoder state, raw byte fields, sensitive/never-indexed handling, reusable output storage, configuration and bounded, streaming decoding with typed errors. `protocol-hpack` supplies the reference behavior and fixtures; an independent Rust codec is only a development dependency, as a differential oracle in tests and fuzzing.

Apply the [protocol switching](protocol-switching.md) requirements in this milestone, to both `base-http1` and `base-http2`: success-status and method mapping, refusal of unsolicited or falsely reported switches, dropping optional HTTP/1 offers without an extended-CONNECT mapping, and HTTP/1 client response classification by the method sent. They land here rather than in M6, which must leave HTTP/1 behavior unchanged, because their cross-version validation needs a second version.

Build the native `base-http2` framing and connection/stream state machines: preface/settings, field blocks and continuations, bodies/trailers, interim responses, flow control, reset, ping and GOAWAY. Keep them usable without a scheduler, under a driver per connection. One driver orders connection output. Stream admission, data-flow credit and retained application memory require separate accounting. Enforce receive windows, header block and field section bounds, and limits on resets and control frames from the first slice.

Extend the HTTP client's existing multiplex integration with HTTP/2 admission, validating reservations at the connection owner's stream-opening boundary. Exercise capacity updates, active-use abandonment and cleanup acknowledgment against the actual HTTP/2 state machine. HTTP/1 and HTTP/2 connections use the same pool contract with their respective capacities. Integrate the `http2` feature into client/server selection and TLS ALPN; add explicit client prior knowledge and optional bounded server preface detection for plain TCP, preserving inspected bytes.

**Exit evidence:** independent HPACK vectors and peer interoperability, including h2spec; malformed compression and frame inputs; concurrent streams, slow consumers, capacity reductions, retained receive data, resets during writes and GOAWAY/open races; each abuse limit. Test an endpoint yielding different negotiated protocols across successive connections in the same client pool. Exercise protocol switches between HTTP/1 and HTTP/2 in every direction as [protocol switching](protocol-switching.md#validation) requires. Stream completion and cancellation must release each charge exactly once. Benchmark concurrency and backpressure as well as peak throughput.

### M8: implement native QUIC as its own transport project

The [QUIC requirements](http3.md#quic-transport-core-and-driver) detail this milestone. Build `base-quic-wire` first, then `base-quic` with a deterministic core accepting datagrams with their addresses and monotonic time, plus a scheduler-owned UDP/timer driver. Integrate rustls's QUIC handshake/key interface. Implement loss recovery and congestion control natively from RFC 9002, as [QUIC](http3.md#quic-transport-core-and-driver) requires, without copied recovery or congestion code; existing QUIC implementations serve as references and independent peers. RFC 9002's NewReno comes first, to establish recovery correctness; CUBIC follows and is the default by the first release, decided on 2026-11-20.

Stage packet parsing/protection and handshake first, then reliable bidirectional/unidirectional streams, acknowledgments/loss recovery, flow control, congestion control and pacing. Add connection-ID routing within the endpoint, transport parameters, path validation, client migration as [QUIC](http3.md#connection-migration-and-preferred-address) requires, and the protocol-required error/closure behavior. Issue every connection identifier through the `base-quic-wire` generator from the first slice, so endpoints can later sit behind the [stateless router](quic-routing.md) without changing. Session resumption and 0-RTT are part of the first release, as decided on 2026-11-20, with their keys and caches in the endpoint and protocol configuration the application constructs. The server's anti-replay state is kept per backend; its mechanism and bound are chosen and recorded in this milestone, as [early data](http3.md#early-data-0-rtt) requires. Establish a tested QUIC v1 baseline before expanding optional transport capabilities. Enable ECN reporting on receive and ECT(0) marking on sockets that carry one path once `base-scheduler` `0.6.0` provides them, as its [packet ECN](../../base-scheduler/design/packet-ecn.md) design and [QUIC routing](quic-routing.md#scheduler-capabilities) describe. Per-datagram ECN on send, GSO/GRO and batched packet I/O are later scheduler capabilities, raised when they are needed.

**Exit evidence:** deterministic simulation of loss, duplication, reordering, delayed acknowledgments and timer expiry; independent QUIC interoperability; slow consumers, stream reset/credit behavior, congestion/recovery, packet-buffer retirement, cancellation and shutdown. The result must carry non-HTTP stream traffic before HTTP/3 depends on it.

### M9: add QPACK and HTTP/3

The [HTTP/3 requirements](http3.md#http3-mapping) detail this milestone. Implement `base-http-qpack` natively behind its own Base-owned interface, like HPACK, as decided on 2026-11-20; an independent codec is only a test oracle. Start with static references and literals, zero advertised dynamic-table capacity and zero blocked streams. Correct instruction/control-stream handling is still required. Add dynamic compression later with explicit blocked-section, acknowledgment and cancellation state.

Implement `base-http3` request streams, control/critical streams, settings, fields/data/trailers, informational responses, error mapping and GOAWAY over `base-quic`. Integrate the `http3` feature into the companion client/server APIs. HTTP/3 uses QUIC stream-opening credit; completion of a local stream does not itself grant another opening. Map protocol switches to extended CONNECT as [protocol switching](protocol-switching.md) requires, and early data as [HTTP/3](http3.md) requires.

**Exit evidence:** independent HTTP/3 peers, invalid/missing critical streams and settings, slow consumers, upload/response concurrency, resets/GOAWAY, trailers and shutdown. Reuse the application semantic scenarios from HTTP/1 and HTTP/2 to expose version-specific gaps.

### M10: route QUIC statelessly by connection identifier

The [stateless QUIC routing requirements](quic-routing.md) detail this milestone. Implement `base-quic-router`: routing decisions over `base-quic-wire` header parsing and server-identifier decoding, tried for every destination identifier before falling back to keyed, weighted rendezvous hashing for identifiers that cannot be routed, per-backend states including draining and weights for new connections, stateless Version Negotiation and a packet-forwarding driver, without TLS, packet decryption or per-connection state. Add the matching receive adapter to `base-quic`. Replies return through the router, by direct server return, or after handoff to a backend's `preferred_address`, as [forwarding](quic-routing.md#forwarding) describes. [Retry offload](quic-routing.md#optional-retry-offload) is optional, and triggers either always or, by default, only above a configured rate. A local backend kind delivers datagrams to an endpoint in the same process through an application-supplied handle, for the load balancer's mixed mode, without `base-quic-router` depending on `base-quic`. The decision logic can be built and tested alongside M7 or M8.

The router and direct server return bind specific addresses and need no new per-datagram addressing in `base-scheduler`; establish UDP address reuse for several processes per host first, as [QUIC routing](quic-routing.md#scheduler-capabilities) requires.

**Exit evidence:** two or more `base-quic` endpoints behind one router address completing handshakes, Retry, client address changes and identifier changes on one backend, with replies through the router, by direct server return and after handoff; delivery to a local backend; backend set and weight changes during handshakes; router memory independent of connection count; no TLS implementation in the router's dependency graph.

### M11: compose the load balancer

The [load balancer requirements](load-balancer.md) detail this milestone. Build the proxy forwarding handler as a library over the client and server, then the load balancer: upstream groups whose clients the policy configures, including their bounded retries, selection, health and draining, replaceable configuration, and a UDP listener on which the router's local backend is the load balancer's own QUIC endpoint. Transformations are [middleware](middleware.md#load-balancer-layers) wrapping each group's client; the first, translating WebSocket handshakes across versions, lives in the load balancer, and without it the proxy forwards only same-mechanism protocol switches and responds 502 to others. Early data reaches the proxy only over HTTP/3 until `base-endpoint` supports TLS 0-RTT; the proxy applies the server's 425 guard and forwards only safe early requests. Prerequisites are client and server deadlines, the [shared request interface](middleware.md#shared-request-interface) with its `ServerContext` carrying the `Peer` and `ClientContext` carrying request options, and, for forwarding CONNECT and protocol switches, managed client tunnels. The proxy handler can start once M7 provides a second HTTP version to forward between; stateless TCP balancing is out of scope.

**Exit evidence:** the three-party proxy scenarios across every pair of enabled versions; WebSocket echo through the load balancer for every pair of versions with the layer, and 502 for a cross-mechanism switch without it; retries bounded by the group client's attempt limit, including cross-member re-decisions; a mixed listener serving stateful and stateless QUIC connections alongside TCP; draining and configuration replacement under traffic; every deadline exercised with stalled peers.

## Measurements and later work

Keep correctness, bounds and lifecycle checks in each milestone. Fuzz parsers/codecs and protocol transitions as those components appear. Preserve provenance, license notices and imported tests for ports and forks.

From M3 onward, compare named workloads on matched hardware and configuration: plain/TLS, protocol version, payloads, concurrency, connection reuse and resource limits. Record throughput, tail latency, CPU, allocations, copies and peak retained/queued bytes. Base's Native readiness and Tokio backends help distinguish protocol effects from io_uring effects; Hyper/Tokio belongs in the external benchmark harness. Optimize the first HTTP/1 path as evidence arrives rather than waiting for HTTP/3.

Dynamic QPACK, specialized provided-buffer paths and more aggressive batching are follow-up decisions driven by concrete workloads or missing capabilities. Multi-origin policies, proxy features beyond the M11 load balancer, compression middleware, expanded tunnel convenience APIs and optional `http`/`http-body`/Tower adapters can be scoped independently after the underlying connection lifecycle works. Separate repository extraction and publishing do not need to interrupt the usable protocol sequence.

The initial semantic/body, HTTP/1 client/server, multiplex-pool integration, HTTP protocol selection and HTTPS slices are implemented. Next extend validation and transport fault injection, assess TLS buffering/performance, and resolve transient borrowed-body forwarding before stabilizing these interfaces; M6 then prepares the connection contract and drivers for HTTP/2.
